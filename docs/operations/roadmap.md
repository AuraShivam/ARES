# ARES delivery roadmap

ARES is planned as a standalone PostgreSQL-backed supply-chain visibility and resilience application. Phase status describes the current local MVP and does not imply production readiness.

| Phase | Scope | Status |
| --- | --- | --- |
| 0. Project foundation | Django, React, PostgreSQL, repository organization, and local setup | Complete locally; PostgreSQL 17 is running and existing ARES records were imported |
| 1. Supply-chain domain and APIs | Suppliers, materials, inventory, purchase orders, shipments, and disruptions | MVP complete |
| 2. Operational workflows | Inventory movement, audit history, overview, demo data, and API workflows | MVP complete |
| 3. Data onboarding and quality | Manual entry, bulk imports, validation, data provenance, and live source ingestion | Complete locally: CSV imports cover all domain records; migrations are applied to PostgreSQL; the GDACS GeoJSON API connector persists current source events and triggers risk assessments/alerts. GDACS is disaster data, not supplier/carrier telemetry. Continuous scheduling belongs to Phase 8; additional supplier/carrier feeds need their own source selection and integration. |
| 4. Risk intelligence and prediction | Explainable risk evidence, shipment-delay prediction, demand forecasting, event-triggered reassessment, threshold alerts, and outcome-based evaluation | Existing risk MVP is locally verified. Experimental shipment-delay and material-demand models are implemented; demand planning includes dated movement imports, 7/30/90-day forecasts, stockout outlook, and advisory reorder/safety-stock estimates. The new movement migration and API still need local runtime verification, and forecasts remain unavailable per material until at least 60 days and 10 distinct issue dates exist. Real-world model accuracy is not established. |
| 5. Disruption response | Reviewable response plans, ownership, approvals, tracking, notifications, and controlled actions | MVP complete and locally checked: an idempotent email outbox routes plan/risk updates to approvers, plan creators, and configured operations recipients with retry tracking; response actions support audited dry-runs and an allowlisted HTTPS webhook behind plan approval, separate approver execution, and an explicit global enable flag. Django's system check is clean, and the dispatcher confirmed email remains disabled by default without changing queued rows. SMTP/recipients/webhook values must be configured locally or in deployment; the notification command needs scheduling for continuous delivery (Phase 8). |
| 6. React dashboard | Operational overview, records, risk assessment, forms, and live updates | MVP complete: authenticated WebSocket invalidation events refresh current API data; the 30-second visible-tab polling remains as a fallback and refreshes immediately when the tab returns. Overview, records, risk intelligence, response plans, imports, operational forms, search/sort, and CSV export are implemented. The frontend production build previously succeeded; the WebSocket addition still needs a browser/runtime check. |
| 7. Security and quality | Automated coverage, access controls, robust errors, and connector/event reliability | Existing API and frontend regression coverage remains complete for the previously verified workflows: all 13 backend tests and 4 frontend tests passed before Phase 8 changes. WebSocket token expiry, reconnect, and post-commit delivery need dedicated coverage; the new socket code has not been exercised in this environment. See the [test guide](../engineering/testing.md). |
| 8. Deployment and operations | Local demonstration, production API and worker deployment, event delivery, backups, monitoring, and recovery | Local and production Compose packages, ASGI WebSockets with Redis, TLS proxy, production settings, background workers, validated PostgreSQL backup/retention, guarded restore script, and runbook are implemented. The local stack is not verified because Docker/Podman is unavailable here. No live production host is planned. Off-host backup and provider alert setup apply only if ARES is later hosted. |
| 9. Supply-chain digital twin | Dynamic dependency graph, coordinates/GeoJSON, impact propagation, what-if simulations, ordered sync recovery, React control-tower UI, and technical documentation | Implemented in source with an additive `0012_digital_twin` migration. Frontend production build and Python syntax checks pass. Backend API/database tests and an authenticated screenshot are pending because this environment lacks the installed Django Channels/Daphne dependencies and a running Docker daemon. No production records or coordinates were fabricated. |

## Recommended order

1. Choose supplier/carrier feed providers only if their data will improve risk decisions; get provider integration details and add source-specific reliability coverage.
2. For local email delivery, configure SMTP only when a demo requires it; outbound response actions remain disabled by default.
3. Run the local demonstration by following the [deployment and operations guide](deployment.md). Use GitHub for source, pull requests, and build automation; GitHub Pages cannot host ARES's Django API and PostgreSQL database.

## Agentic AI and resilience-intelligence expansion

This workstream follows the requirements in the master development prompt and extends the existing product phases above.

| AI work phase | Scope | Status |
| --- | --- | --- |
| 1. Data readiness and shared contracts | Read-only data readiness API; explicit coverage, provenance, freshness, and model data gaps; validated, provider-neutral agent result contract | Implemented locally; focused tests are present. Test execution remains pending because the current backend virtualenv is missing `daphne`; see [agentic AI foundation](../engineering/agentic-ai-foundation.md) |
| 2. Agent runtime and provider abstraction | Configurable provider, disabled/unavailable state without credentials, execution lifecycle and read-only tools | Implemented locally: bounded execution, OpenAI Responses adapter behind a provider boundary, authenticated status/tools/execution APIs, per-user idempotency and history, validated evidence-only results, and human-approval recommendations. Remains disabled unless an operator explicitly opts into external processing. No live provider call or credentials are configured. See [agentic AI foundation](../engineering/agentic-ai-foundation.md). |
| 3. Specialist agents and coordinator | Risk, supplier, inventory, logistics, procurement agents with structured coordination | Implemented locally: five role-focused specialists run sequentially with role-specific read-only tool access; the coordinator accepts a bounded specialist selection, records each stage, and synthesizes only verified evidence under shared timeout and tool-call budgets. Focused tests are added; Django tests and migration checks are pending because local `.venv` is missing `daphne`. No live provider call has been made. See [agentic AI foundation](../engineering/agentic-ai-foundation.md). |
| 4. Predictive model evaluation | Chronological baselines/comparison, calibration, reproducible evaluation and persisted metrics | Implemented locally: authenticated API and management command evaluate shipment delay and demand forecasts using chronological holdouts, transparent baselines, calibration diagnostics, saved metrics, and data fingerprints. Runtime evaluation remains data-dependent; the migration and benchmark still need to be applied/run on configured PostgreSQL with enough verified outcomes and dated movements. Metrics do not calibrate production predictions or establish generalization. See the [evaluation guide](../engineering/predictive-model-evaluation.md). |
| 5. Disaster and geospatial exposure | Improve source event lifecycle/geometry handling and evidence-based exposure paths | Implemented locally: GDACS GeoJSON is validated and lifecycle-aware; map views include source polygons, source metadata, and optional supplied shipment paths; exposure separates explicit operational links, polygon intersections, policy-buffer proximity, dependency paths, unaffected, and unknown with structured evidence. Coordinates and shipment paths remain optional input data; migration and live-feed verification on the user's PostgreSQL runtime are pending. No geocoding, route inference, or GDACS-to-operational-impact assumption is made. |
| 6. Recovery strategy simulation | Compare verified supplier, stock redistribution, emergency procurement and route options in isolated simulations | Implemented locally: isolated, persisted what-if comparisons support verified supplier candidates, warehouse transfers, emergency procurement, operator-sourced route alternatives, and explicitly grouped combinations. Configurable objective weights show metric coverage and limitations. Frontend production build and Python syntax checks pass. No recovery action is executed; current capacity, quotes, location-level demand, and route services remain unavailable. Database-backed API verification remains pending. |
| 7. Outcome tracking and calibration | Connect predictions, approved actions, verified outcomes and effectiveness reporting | Implemented in source: shipment predictions can be retained as immutable, deduplicated point-in-time snapshots; shipment and disruption outcomes require approver evidence and explicit intervention attribution; disruption labels link to the exact reviewed risk snapshot; completed response plans retain evidence-backed effectiveness reviews tied to action outcomes. The risk dashboard reports outcome coverage, no-intervention Brier/reliability summaries, intervention counts, and reviewed plan/action effectiveness. These are retrospective descriptive metrics, not automatic recalibration or causal estimates. Apply migration `0017_outcome_tracking` and verify the workflow against the configured PostgreSQL demo before presenting it as runtime-verified. No production labels or prediction snapshots are seeded. See the [risk intelligence](../product/risk-intelligence.md), [response plans](../product/response-plans.md), and [agentic AI foundation](../engineering/agentic-ai-foundation.md) guides. |
| 8. Human-reviewed end-to-end coordination | Orchestrate disruption-to-recommendation workflow and approval handoff | Implemented locally: an authenticated, bounded coordinator workflow is pinned to a selected disruption and exact risk-assessment snapshot; evidence-backed recommendations can be handed to an audited response-plan draft. Human review and approval remain required. Apply migration `0018_human_reviewed_workflows`; database-backed workflow and configured-provider verification remain pending. |
| 9. Agentic and predictive dashboard | Agent control centre, model evaluation, enhanced simulation views | Implemented locally: the AI Control Center shows measured capability readiness, runs bounded role-based agents and coordinators, displays evidence/stages/history, and launches persisted shipment-delay or demand evaluations with baseline metrics. The Digital Twin now lists and reopens saved simulation results. Frontend build and Python syntax checks pass; Django/runtime verification requires the user's PostgreSQL Compose environment. External provider execution remains opt-in. |
| 10. Integrated reliability and governance | Agent-specific security, timeouts/retries, audit, prompt/model governance and complete integration coverage | Partially implemented at core-platform level |
| 11. Documentation and demonstration | End-to-end architecture, provider configuration, operations runbook and demonstration flow | Phases 1 through 9 APIs, configuration, orchestration, model evaluation, disaster exposure, recovery simulation history, outcome tracking, evidence-backed response handoff, data handling, and limitations documented; end-to-end demonstration and live-provider verification remain pending |

The measured requirements for supplier alternatives, shipment routes, and training history are listed by `GET /api/ai/data-readiness/`. Phase 3 adds sequential specialist analysis and coordinator synthesis on top of the bounded read-only runtime. Existing ARES capabilities are reused; this expansion does not replace the risk rules, current forecast implementations, or digital twin.
